# 검증 예산 가드 + 체크포인트 일시정지 설계

- 작성일: 2026-09-01
- 상태: 승인됨

## 1. 배경 및 목적

v1 콘텐츠 생성 파이프라인은 코드 레벨에서 완성됐고(`docs/STATE.md` 기준), 남은 건 계정/API 키 등 사람이 해야 하는 셋업뿐이다. 하지만 실제로 파이프라인을 돌리기 시작하면 다음 현실에 부딪힌다.

- 영상 1편당 원가는 $3~5 (`orchestrator.estimate_cost()` 기준).
- YouTube Shorts 수익화 문턱은 **구독자 1,000명 + Shorts 조회수 1,000만회(90일 이내)** 또는 **롱폼 시청시간 4,000시간** — 영상을 몇 개 만든다고 도달이 보장되는 게 아니다.
- 즉, 수익화 여부가 검증되지 않은 상태에서 실제 돈이 계속 나간다. 조회수가 안 나오면 아무리 영상을 많이 만들어도 문턱에 도달하지 못한 채 비용만 쌓일 수 있다.

이건 전형적인 "검증되지 않은 가설에 실제 비용을 태우는" 상황이다. 이번 설계는 **손실 한도를 미리 정하고, 그 한도 안에서 사람이 주기적으로 성과를 확인하도록 시스템이 강제**하는 안전장치를 추가한다.

**핵심 원칙**: 판단(계속/중단/방향전환)은 사람이 한다. 강제(한도를 넘기지 못하게 막는 것)는 시스템이 한다. 조회수/구독자 데이터를 자동으로 분석해 판단을 대신하는 것은 이번 범위가 아니다 — 그건 설계 문서(`2026-08-31-ai-shorts-content-pipeline-design.md` §8)에서 이미 v1 범위 밖으로 분류한 "성과분석/최적화 루프" 서브프로젝트의 몫이다.

## 2. 확정된 파라미터

논의를 통해 확정:

- **검증 단계 총예산**: $125 (사용자가 부담 없다고 느낀 $100~150 범위의 중간값)
- **체크포인트 주기**: 영상 10개마다 (하루 1편 기준 약 10일 간격, 20~30개 예산 안에서 2~3회 체크포인트)
- **예산 소진 시**: 그날 실행 거부, 예산을 올리거나 중단할지는 사람이 결정
- **체크포인트 도달 시**: 그날 실행 거부, 사람이 YouTube Studio를 확인하고 명시적으로 재개 신호를 줘야 재개

## 3. 설정값

GitHub Actions **저장소 Variables**로 관리 (시크릿 아님 — 민감정보가 아니고, 사람이 수시로 값을 바꿔야 하므로 Secrets보다 Variables가 적합):

| 변수 | 기본값 | 의미 |
|---|---|---|
| `VALIDATION_BUDGET_USD` | `125` | 검증 단계 누적 지출 상한 |
| `VALIDATION_CHECKPOINT_EVERY` | `10` | 몇 편마다 자동 일시정지할지 |
| `VALIDATION_ACK_COUNT` | `0` | 사람이 마지막으로 검토를 마친 영상 수 (검토 후 사람이 직접 갱신) |

이 값들은 워크플로(`.github/workflows/daily-shorts.yml`)의 `env:` 블록에 `${{ vars.VALIDATION_BUDGET_USD }}` 형태로 전달된다.

## 4. 동작 로직

`orchestrator.py`에 검증 가드 함수를 추가하고, 기존 `_preflight_check`(환경변수 확인)와 같은 위치 — **아이디어 생성 등 첫 유료 호출이 일어나기 전** — 에서 호출한다.

```
검증 가드(state):
  누적_지출 = state.cost_log의 cost_usd 합계
  누적_영상수 = len(state.cost_log)

  if 누적_지출 >= VALIDATION_BUDGET_USD:
      알림("검증 예산 소진: $누적_지출 / $VALIDATION_BUDGET_USD. "
           "계속하려면 VALIDATION_BUDGET_USD를 올리거나, 여기서 중단하세요.")
      실행 중단, 아무것도 생성하지 않음

  if 누적_영상수 >= VALIDATION_ACK_COUNT + VALIDATION_CHECKPOINT_EVERY:
      알림(f"체크포인트 도달: 영상 {누적_영상수}편, 누적 ${누적_지출:.2f} 지출. "
           f"YouTube Studio 확인 후 계속하려면 VALIDATION_ACK_COUNT를 {누적_영상수}(이)로 올리세요.")
      실행 중단, 아무것도 생성하지 않음
```

두 조건 모두 **막는 것**(시스템의 역할)이지 **판단하는 것**(사람의 역할)이 아니다. 사람이 `VALIDATION_ACK_COUNT`를 올리는 행위 자체가 "검토를 마쳤다"는 증거가 되고, 파이프라인은 그다음부터 다시 정상 동작한다. `VALIDATION_BUDGET_USD`를 올리는 것도 마찬가지로 "검증 단계를 연장하기로 했다"는 의도적 결정을 코드가 아니라 사람이 GitHub 설정에서 직접 하게 만든다.

두 조건 모두 예산/체크포인트 소진 시 **아무 비용도 발생하지 않고 즉시 중단**된다 — 기존 `_preflight_check`처럼 이 가드도 아이디어 생성(첫 유료 호출) 이전에 실행되어야 한다.

## 5. 알림 메커니즘

`telegram_approval.py`에는 현재 승인 요청용 `request_approval()`(버튼 있는 양방향)만 있다. 이번에 **단방향 알림 함수** `notify(text: str) -> None`을 추가한다 — 버튼 없이 텍스트 메시지만 전송하고 응답을 기다리지 않는다.

이 함수는 검증 가드 알림뿐 아니라, `todo.md`에 "나중에" 항목으로 남아있던 **"파이프라인 실패 시 텔레그램 알림 없음"** 문제도 같은 함수로 해결한다 — `orchestrator.py`의 예외 처리 경로에서도 재사용 가능. (이번 구현 범위에 실패 알림 배선까지 포함할지는 구현 계획 단계에서 확정 — 최소한 `notify()` 함수 자체는 이번에 만든다.)

## 6. 상태 추적

새로운 상태 파일이나 스키마 변경은 필요 없다 — `state/history.json`의 기존 `cost_log`(영상별 비용)와 그 길이(영상 수)만으로 두 조건을 계산할 수 있다. `VALIDATION_ACK_COUNT`는 상태 파일이 아니라 GitHub 저장소 Variable에 저장되므로(사람이 직접 관리), state.py 변경도 불필요하다.

## 7. 테스트 관점

- 예산 미달 + 체크포인트 미달 → 가드 통과, 정상 진행 (mock으로 확인)
- 예산 초과 → 가드가 차단하고 `notify()`가 호출되며, 이후 어떤 유료 함수(`ideas.generate_idea` 등)도 호출되지 않음을 확인
- 체크포인트 도달(`ACK_COUNT + CHECKPOINT_EVERY` 이하로 영상 수 도달) → 동일하게 차단 확인
- `VALIDATION_ACK_COUNT`를 올린 뒤에는 다시 통과하는지 확인 (경계값 테스트)
- `notify()` 자체는 기존 `telegram_approval.py` 테스트 패턴(모킹된 `requests.post`)을 따라 별도 테스트

## 8. 범위 밖

- 조회수/구독자/시청시간 등 YouTube 분석 데이터를 API로 자동 수집·판단하는 것 — 다음 서브프로젝트(성과분석/최적화 루프)의 몫.
- 체크포인트 판단을 텔레그램 버튼(승인 게이트처럼)으로 자동화하는 것 — 이번엔 GitHub 저장소 Variable을 사람이 직접 수정하는 방식으로 충분히 단순하게 유지.
- 검증 단계 종료 후("문턱 도달" 또는 "확실히 안 됨"으로 판단된 이후) 이 가드를 자동으로 끄거나 완화하는 로직 — 예산값을 사람이 직접 올리는 것으로 충분 (YAGNI).
